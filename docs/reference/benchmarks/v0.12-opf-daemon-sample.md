# v0.12 Warm OpenAI Privacy Filter Sample

**Run date:** 2026-07-10

**Gaze revision:** `4c2b74f5e509f61a7369c848b90703b992754ecc`

**Decision:** warm OpenAI Privacy Filter is a promising recall upgrade,
especially for English, but it is not a safe drop-in SafetyNet replacement yet.

This is a 50-document diagnostic sample from the frozen English/German Dataiku
test split, not the promotion baseline. The production recognizers and policy
were unchanged. The benchmark harness adds an optional OPF Resolve cell, a
private Unix-socket daemon bridge, and fail-closed availability accounting.

| Gaze policy | Pass 2 + OPF, `Resolve` with `Redact` fallback |

The daemon keeps the OPF Python runtime and checkpoint resident. Gaze still
launches its small subprocess client for each SafetyNet call, preserving the
existing adapter's stdin/stdout JSON contract. This is a benchmark deployment
shape; the pinned upstream OPF CLI does not itself expose a daemon subcommand.

Gaze verified the checkpoint bundle before first inference. That one-time hash
and initialization produced a 168.3-second start-to-first-response time and is
excluded from warm percentiles.

## Blocking failures

The recall win does not compensate for failures on other axes:

- one German document failed closed because OPF returned an offset that Gaze
  rejected as an invalid UTF-8 boundary;
- repeated runs produced different spans for the same German input, including
  both successful and invalid-boundary results;
- OPF reported 90 class mismatches and strict mode would reject 47 of the 49
  completed documents;
- only 9 of 49 completed documents restored exactly, although restore telemetry
  reported `success` for all 49;
- 158 suspects remained after policy application, leaving only 8 of 49
  post-policy scans clean;
- the benchmark process sustained 0.164 documents/second including checkpoint
  verification. A full 1,886-row run in this shape is roughly an 80–90 minute
  job on the measured CPU.

The restore and manifest failures exercise the same existing Resolve-coordinate
and irreversible-fallback defects found by the Kiji baseline. OPF discovers
more spans and far more class mismatches, so those defects affect more documents.

## Reproduction

Install and verify the pinned OPF bundle using the project fetch/setup path.
Start the warm daemon in one terminal:

```bash
<opf-venv>/bin/python scripts/bench/opf_daemon.py serve \
  --socket target/bench-opf/opf.sock \
  --checkpoint <opf-checkpoint> \
  --device cpu
```

Run the sampled scorecard in another terminal:

```bash
uv run --with pyarrow scripts/bench/dataiku_en_de_gaze_bench.py \
  --no-download \
  --config full-stack-opf-resolve \
  --max-documents 50 \
  --opf-command scripts/bench/opf_daemon.py \
  --opf-checkpoint <opf-checkpoint> \
  --opf-daemon-socket target/bench-opf/opf.sock
```

## Required work before promotion

1. Define and test the OPF character-offset to Gaze UTF-8-byte contract; make
   repeated CPU inference deterministic or fail with a typed stable reason.
2. Repair manifest-backed Resolve promotion and replace irreversible fallback
   semantics when exact restore is required.
3. Treat residual post-policy suspects as a closed failure, not a successful
   clean result.
4. Productize a supervised persistent OPF transport with authentication,
   lifecycle management, bounded queues, and no PII-bearing logs.
5. Re-run all 1,886 frozen rows plus negative-only and agentic JSON/streaming
   corpora before comparing it as a replacement.
