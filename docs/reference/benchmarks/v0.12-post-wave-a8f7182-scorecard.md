# v0.12 Post-Wave Scorecard: `main` at `a8f7182`

This report measures current `main` (`a8f7182`, the tip after the 2026-08-17/18
merge wave) against `18fd9e2`, the merge commit of PR #427 — the last merge whose
content had been scored against the corpus. It settles the merges that shipped on
unit tests and gates alone, in particular the shipped-default safety-net leak fix
(#436, todo #2956) and the daemon safety-net registry (#446). It is evidence only:
no accepted baseline was installed or modified, and `--accept-baseline` was not
used.

## Headline

**The shipped-default cell (`full-stack-kiji-resolve`, SafetyNet `resolve` +
`redact` fallback) leaks more labeled bytes on the candidate: 30,686 → 31,995
(+1,309 bytes, leak rate 23.5535% → 24.5583%), fully covered entities
10,098 → 10,008 (−90), zero-leak documents 1,119 → 1,111 (−8).** The
`compare_scorecards(candidate, base)` pairwise gate returns
`regression.passed = false` on that cell (five count gates plus 21
`class_coverage_loss` rows). The two deterministic cells (`rule-floor-extended`,
`pass2-ner`) are byte-identical to the base in every correctness integer.

The same cell in the same run: false-positive bytes 182,950 → 168,163
(−14,787), redact actions 6,802 → 1,609 (−5,193), manifest spans (restorable
tokens) 31,734 → 37,270 (+5,536), post-policy residual suspects 1,865 → 325
(−1,540), exact restores unchanged (2,277), documents with a redact unchanged
(633), fail-closed 0 → 0. The candidate is not release-ready and neither was the
base; the ten zero-target readiness gate names are the same on both halves.

The regression is almost entirely German: `de` leaked 12,884 → 14,209
(+1,325), `en` 17,802 → 17,786 (−16). The largest label movers are
`TAXNUM` +151, `NATIONALID` +121, `ZIP` +112, `IDCARDNUM` +111, `PASSWORD` +102,
`BUILDINGNUM` +102 (details below).

Restore decision failures stay at 5 / 5 / 5 per cell on both halves — the
pre-existing, base-identical defect tracked as todo #2415. That count did not
change; it is not news.

### Basis choice

The last committed scorecard (`v0.12-government-id-scorecard.md`) measured PR
#427's head `b0f21b7` against `ce11278`. `b0f21b7` was never rebased and is
**not an ancestor of `main`**, so it cannot serve as the base of a `main`-to-`main`
comparison. `18fd9e2` is #427's actual merge commit and the first `main` tree
that contains all three previously scored changes (#423, #425, #427). Measuring
against it isolates exactly the fifteen merges after it (listed below).

To close the gap between the last scored tree and `18fd9e2`, the fresh BASE
scorecard was also compared against the committed `b0f21b7` scorecard
(`785c2223…`, same dataset hash, same model bundles). Both deterministic cells
are byte-identical in every correctness integer, so the merges between them
(#426 which `b0f21b7` lacked, #428, #429, #430, #431, #432, and the rebase onto
#425) have no rule-floor or pass2 effect. The Kiji cell differs in the pattern
the committed Kiji-decoder scorecard already documented for #425 (restore
failures 557 → 633, FP bytes 179,771 → 182,950, leaked 30,691 → 30,686); it is
not re-analyzed here.

## Interpretation

What moved is confined to the safety-net `resolve` path, and it moved in the
direction #436 describes. On the base, when the resolve pass converged and the
re-run still flagged a residual, `apply_safety_net_fallback` redacted the
**primary** report at pre-resolve coordinates on the post-resolve text: it
deleted freshly minted tokens (dropping their manifest entries) and redacted
whatever bytes the stale offsets now pointed at. That accidental over-redaction
is what the base's numbers show as 5,193 more redact actions, 5,536 fewer
restorable tokens, and 14,787 more false-positive bytes. On the candidate the
fallback acts on the residual report at correct coordinates and preserves
tokens; the redact count, FP bytes and residual suspects all fall and the
manifest grows.

The +1,309 leaked labeled bytes are the other side of the same change: gold
bytes — overwhelmingly German, concentrated in numeric identifier and address
labels (`TAXNUM`, `NATIONALID`, `ZIP`, `IDCARDNUM`, `BUILDINGNUM`, …) — that the
base deleted by accident under the stale-coordinate redaction, and that no
detector (rule floor, pass2 NER, Kiji at its true position) protects on the
candidate. They were never detected on either half; on the base they did not
ship (as the protection trace records it) because a restore-destroying
redaction happened to fall on them. Under
axis 1 the corpus measure of the shipped default nevertheless got worse by 1,309
bytes and 8 zero-leak documents, and it is reported as such. Under axes 2 and 4
the candidate is materially better (5,536 more restorable tokens at unchanged
exact-restore count, one audit row per fallback action, residual suspects
surfaced in the report).

This attribution to #436 rests on the mechanism #436 documents and on the shape
of the deltas (redact −5,193 ≈ manifest +5,536; DE-concentrated; unchanged
FP-document count), not on a per-PR bisect. #435 (resolver `arbitrate()`) and
#440 (structured walker) also touch the runtime; both deterministic cells being
byte-identical bounds #435 to safety-net interactions and #440 to structured
documents, neither of which this corpus exercises directly. A one-run
attribution — the same command at `d64d7e3` (the parent of #436) — would split
the fifteen merges at the leak fix and is the recommended next step before any
patch-release decision that cites this number.

## Determinism

The README's last target row requires the complete three-cell correctness
integers to be exactly equal across two full runs. CANDIDATE was run twice
(`a8f7182`, `dirty = false` both times, same worktree, back to back).
The two candidate scorecards agree exactly: in every cell the complete
`_run_correctness_counts` integer set is equal, the entire run object is equal
once the timing sections (`latency_ms`, `warm_latency_ms`, `process`) are
excluded, and `compare_scorecards(run 2, run 1)` returns
`regression.passed = true` with zero failures. Run 2 executed under the load
spike disclosed above and still reproduced run 1 byte for byte in every
correctness field, so the +1,309-byte headline is a stable property of
`a8f7182`, not a flip. `compare_scorecards(run 2, base)` returns the same 26
failures as run 1. Wall clock (build + three cells): BASE 694 s, CANDIDATE run 1
675 s, CANDIDATE run 2 768 s.
