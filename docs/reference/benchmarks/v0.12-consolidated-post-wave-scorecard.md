# v0.12 Consolidated Post-Wave Scorecard

This report measures the **composed** effect of the two `core` rulepack recognizers that the
detection wave drained onto `main` — `url.anchored` and `security_token.anchored` — on shipped
`main` at `38334d0`. Every prior number for that wave was a per-PR delta; nothing had measured the
two together.

It characterizes evidence only. It proposes no detector, model, runner, scorer, probe, policy,
comparator, fixture, or readiness change. No accepted baseline was installed or modified, and
`--accept-baseline` was not used.

Both halves completed all three cells at 2,910/2,910 documents. **This is the first run in this
benchmark's history in which `full-stack-kiji-resolve` completed at all** — see
[Cell completion](#9-cell-completion).

## Basis construction

The comparison is subtractive: it takes shipped `main` and removes only the subject, rather than
building the pre-wave tree forward. Three earlier attempts failed because the benchmark instrument
itself — `clean_for_bench.rs`, the deterministic ORT session, the session-hex seam, the negative
corpus, and all of `scripts/bench` — arrived on `main` with the same drain that carried the
recognizers. A pre-drain tree structurally cannot host the current instrument.

```
candidate = origin/main @ 38334d0
base      = 38334d0 with crates/gaze-recognizers/embedded/core.toml
            taken verbatim from c5b9af0 (the direct parent of drain commit 609172e)
```

To reproduce in six months:

```sh
git fetch origin main
git checkout -b bench/candidate 38334d0
git checkout -b bench/base 38334d0
git checkout c5b9af0 -- crates/gaze-recognizers/embedded/core.toml
git commit -s -S -m "revert core.toml to c5b9af0 for the BASE half"
```

Why the construction is exact, verified before measuring:

| Check info | Result info (observed) |
| --- | --- |
| `git diff --stat c5b9af0 origin/main -- crates/gaze-recognizers/embedded/` | `core.toml \| 128 +++` — one file, +128 |
| Deletion count in that diff, grepped independently | **0** |
| `git diff 38334d0 <base-commit> --stat` | `core.toml \| 128 ---` — one file, nothing else |
| sha256 of BASE `core.toml` | `7799f39f58b9e48ef59ccd59ecb4a24cfa8c6567aef4ab5d609d692e03cc95cb` |
| sha256 of `c5b9af0:crates/gaze-recognizers/embedded/core.toml` | identical to the above |

Because the wave only **appended** to `core.toml` and deleted nothing, reverting the file is exactly
"minus those two recognizers" — no hunk surgery and no judgement call. `crates/gaze-recognizers/src/lib.rs:47`
embeds the file via `include_str!`, so cargo fingerprints it and the revert propagates into the binary.
That was verified rather than assumed: the built BASE probe contains **0** occurrences of both
`url.anchored` and `security_token.anchored`.

Everything else — `pipeline.rs`, the Kiji ORT determinism work, the session-hex seam,
`clean_for_bench.rs`, the validator probe, the negative corpus, all of `scripts/` — is byte-identical
across the halves. Those changes sit in **both** halves and their effect is therefore *not* isolated
by this run. The result must be read as "the composed effect of the two drained `core`-rulepack
recognizers, measured on current `main`", **not** as "the composed effect of PR #413".

### Two required disclosures

1. **`crates/xtask/snapshots/core-no-policy.json` and the redaction-classes drift gate disagree with
   the BASE tree's `core.toml`.** The BASE tree is internally inconsistent with its own committed

   `run_no_opf_benchmark.py` and `gaze_bench_score.py`, so neither the runner nor the scorer reads it.
2. **`crates/gaze-recognizers/tests/url_anchored.rs` and `tests/security_token.rs` would fail on the
   BASE tree**, because those recognizers are deliberately absent from it. Crate tests are not part of
   this profile and were not run as part of it.

### Why the +56 is real and not a counting artifact

Per-class leaked bytes do not sum to the cell-level total, because overlapping and adjacent gold
spans are merged at cell level while a byte covered by two overlapping labels is counted once per
label:

| Cell info | Σ per-class leaked, BASE info (observed) | Cell leaked, BASE info (observed) | Overcount info | Σ per-class leaked, CANDIDATE info (observed) | Cell leaked, CANDIDATE info (observed) | Overcount info |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `rule-floor-extended` | 112,616 | 112,453 | +163 | 103,156 | 103,003 | +153 |
| `pass2-ner` | 44,685 | 44,561 | +124 | 37,833 | 37,710 | +123 |
| `full-stack-kiji-resolve` | 40,331 | 40,225 | **+106** | 34,576 | 34,470 | **+106** |

`entities` and `fully_covered` sum exactly in every cell; only bytes overcount, exactly as the merge
semantics predict. The overcount is **identical (106) on both Kiji halves**, so it cancels in the
delta and cannot explain the +56. In the two deterministic cells the overcount does shift (163→153,
124→123), which is precisely why their per-class sums reconcile to the cell delta off by −10 and −1
respectively. No integer is unaccounted for.

Cell-level `leaked_labeled_utf8_bytes` is the authoritative headline number; per-class figures are
directional evidence, sound here because the Kiji overcount is constant across halves.

## 10. The fail-closed population moved; it did not vanish

A fail-closed count dropping 660 → 0 has two possible readings with opposite meanings: the documents
no longer *need* to fail closed, or a check stopped firing. The distinction was tested, not assumed.

**The scored population absorbed exactly the historical fail-closed count.** From the committed
`v0.12-no-opf-scorecard-v3.json`:

| Cell info | v3 scored docs info (observed) | v3 PII bytes info (observed) | v3 leaked info (observed) | This run, BASE scored docs info (observed) | BASE PII bytes info (observed) | BASE leaked info (observed) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `rule-floor-extended` | 2,910 | 130,282 | 112,453 | 2,910 | 130,282 | **112,453** |
| `pass2-ner` | 2,910 | 130,282 | 44,561 | 2,910 | 130,282 | **44,561** |
| `full-stack-kiji-resolve` | **2,250** | **94,037** | 30,693 | **2,910** | **130,282** | **40,225** |

Four findings follow.

1. **The instrument is stable.** The two deterministic cells reproduce the committed v3 baseline
   **byte-for-byte** on leaked bytes, false-positive bytes, PII bytes and `restore_success_decisions`,
   across a v3 → v4 instrument change and a tree 58+ commits newer. That is independent evidence the
   harness and the basis are sound.
2. **The Kiji cell's scored population grew 2,250 → 2,910, exactly +660** — the historical fail-closed
   count — bringing **+36,245 previously unscored PII bytes** into the denominator.
3. **The apparent kiji increase is a denominator change, not a detection regression.** The leak rate
   *fell*, 32.64% (30,693 / 94,037) → 30.88% (40,225 / 130,282). The 660 re-entrants leaked 9,532 of
   their 36,245 PII bytes (26.31%), a *lower* rate than the previously-scored population.
4. **The 660 did not become silently accepted.** Clean-accepted rose only 982 → 994 (+12) while
   `strict_would_reject` rose 1,268 → 1,916 (+648). 98% of the re-entrants are still refused by the
   strict gate. The safety signal moved from one refusing bucket to another, and did not evaporate.

**Stated limit of this evidence.** No document in the 2,910-document corpus fails closed on the

fail-closed document. The path is proven *present* and *typed*, and its emission shape is proven to
match what the scorer keys on; it is not proven *reachable by corpus input* on `38334d0`. The absence
is the finding, and the residual risk is that a regression silencing this path would look identical
in this corpus. A synthetic fault-injection fixture would close that gap and is out of scope for a
characterization run.

## Interpretation notes

**PR #418 plausibly raises measured leaked bytes, and that is correct behaviour.** The panic fix
changed redaction semantics so overlapping deletions remove exactly the union of flagged spans, where
the previous code could consume an arbitrary run of unflagged text past the flagged region.
Over-deletion incidentally removed bytes the scorer counts as leaked. Deleting less — which is
correct — can therefore *raise* the leaked-byte count. This run cannot isolate that effect, because
#418 is present in both halves. It is recorded so a future reader does not misread a leaked-byte
increase across the #418 boundary as a detection regression: every flagged byte is still removed, and
axis 1 is not weakened by retaining unflagged text.

**What this run does not measure.** The drain's `pipeline.rs`, Kiji determinism and session-hex
changes are in both halves, so their effect is not isolated. Neither is #418's or #419's.
