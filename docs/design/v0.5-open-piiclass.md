# v0.5 Open-key PiiClass Design

Status: design sketch for v0.5 review. This is spec-only context landed in
v0.4.2. It does not change source behavior.

Freshness anchor: file and line citations below were verified against
`origin/main` commit `791c79daa58587be19326a5e41f2f564e38082f1` before this
document was written.

Primary inputs: scratchpad 258 rev 3 §S5; scratchpad 256, "Brainstorm
synthesis — Crate shape v0.4.x (#117)" §LOCK 2; drawer `eac549ae` for
north-star axes 5 and 3; drawer `e8b5c041` for the three-surfaces distinction;
the pending crate-shape decision drawer for v0.5 review; and architecture drawer

## Motivation

The v0.5 `PiiClass` refactor should serve north-star axis 5, adopter
ergonomics, and axis 3, agentic-first fit. Adopters should be able to introduce
domain-specific classes for agent workflows without changing Gaze source,
waiting for a release, or threading a custom enum variant through every
consumer. The current design can express custom classes, but the ergonomics are
visibly second-class: `PiiClass::Custom(String)` renders as token families such
as `<Custom:case_ref_1>`, which is verbose and makes neutral adopter classes
feel bolted onto the built-in grammar.

The current closed enum is also spreading match-exhaustiveness boilerplate
through consumers that are not semantically choosing between built-in classes.
The detector type owns `PiiClass::Email`, `PiiClass::Name`,
`PiiClass::Location`, `PiiClass::Organization`, and `PiiClass::Custom(String)`
at `crates/gaze/src/detector.rs:9-16`; helpers then expose built-in arrays and
class-name formatting at `crates/gaze/src/detector.rs:18-85`. Downstream
surfaces must repeatedly match built-ins plus `Custom`: session token
formatting, token-shape traps, redaction-log storage, rulepack parsing, policy
parsing, generalization, resolver priority, CLI context dictionaries, NER label
maps, tests, and docs.

`PiiClass::Custom(String)` works today and preserves reversibility, but it keeps
custom classes in a namespace with a different visible grammar. v0.5 should make
"class is a normalized key" the core model. Built-ins remain reserved keys with
default behavior; new adopter classes become ordinary keys in the same type. The
goal is not to add a weaker free-form escape hatch. The goal is to make
class-key extensibility reliable, manifest-restorable, auditable, and natural
for agentic workflows.

This section cites scratchpad 256 because the same brainstorm synthesis that
defers crate-shape Option B also requires the open-key `PiiClass` refactor to be
bundled with any SemVer-breaking crate-shape change. The open-key decision is a
v0.5 design-review topic, not a v0.4.2 implementation.

## Open-key PiiClass

Proposed shape:

```rust
pub struct PiiClass(Symbol);
```

`Symbol` is intentionally placeholder wording for the v0.5 design review. The
implementation may use `String`, `Box<str>`, `Arc<str>`, or an interner. The
public contract is that `PiiClass` is an owned, normalized class key with stable
serde behavior and no closed built-in enum variants.

Normalization rules:

- Canonical class keys are lowercase ASCII identifiers.
- Unquoted token class names use `[a-z][a-z0-9]*`.
- Empty class names are invalid.
- Names with `:`, `_`, non-ASCII, or other punctuation require quoted token
  grammar and must remain byte-for-byte manifest-restorable.
- The v0.5 implementation must choose one normalization API and use it in
  policy, rulepack, context, registry, redaction log, token shape, and snapshot
  decode paths. No caller should need to know whether a class was formerly
  built-in or custom.

Reserved built-in names:

- `email`
- `name`
- `location`
- `organization`

Reserved-name policy:

- Built-in names are reserved at registry load and policy/rulepack load.
- Built-in recognizers may emit reserved names.
- Adopter rulepacks and policy custom recognizers may reference reserved names
  only when they intend to cooperate with the built-in class semantics.
- A custom class declaration that tries to redefine a reserved built-in name
  fails closed.
- Collision error: `RulepackError::ReservedClassName { name: String }`.
- Policy-side collision error: `PolicyError::ReservedClassName { name: String }`.
- Malformed key error: `PolicyError::OpenKeyClassMalformed { value: String }`
  and `RulepackError::OpenKeyClassMalformed { value: String }`.

Restore grammar:

- Session-prefixed token, unquoted class:
  `<{session_hex}:Class:caseref_1>` for any class key that does not require
  quoting.
- Legacy-compatible built-in rendering may keep `<{session_hex}:Email_1>` only
  as a decode alias during migration. New v0.5 open-key emission should use one
  canonical grammar for all classes.
- Quoted class names use JSON-string escaping inside the class slot:
  `<{session_hex}:Class:"case:ref"_1>` and
  `<{session_hex}:Class:"case_ref"_1>`.
- The counter suffix remains outside the class string. The final `_N` belongs to
  the token, not to the class.
- A class string containing `:` or `_` must be quoted when ambiguity would make
  the split between class and counter non-deterministic.

Round-trip invariant: v0.5 open-key tokens MUST remain manifest-restorable.
No one-way primitive, irreversible redaction token, or lossy class rewrite is
introduced by this design. Snapshot import must either decode the class key
exactly or fail closed.

Three-surfaces invariant: policy documents define classes and recognizers;
runtime knobs tune execution; CLI flags expose selected runtime knobs. Per
drawer `e8b5c041`, this design does not imply every future class definition gets
a CLI flag. CLI overrides remain narrow and explicit.

Registry invariant: same-class recognizer cooperation remains required under
open-key classes. The current validator rejects same-class recognizer pairs that
omit `cooperates_with` at `crates/gaze/src/rulepack.rs:435-456`. v0.5 must
preserve that invariant for any normalized class key, including adopter-defined
classes.

Neutral examples only: examples in this document use classes such as `case_ref`,
`ticket_ref`, and `asset_ref`. They are not proposed built-ins.

## Reserved-name and collision policy

Concrete rules: the reserved set is exactly `email`, `name`, `location`,
`organization`; reserved names are lowercase canonical keys; built-in
recognizers may emit them; adopter rulepacks may reference them only to
participate in existing class semantics; custom declarations that redefine them
fail before recognizer registration; malformed class-key parsing fails closed;
redaction logs store only normalized class keys, never raw values or token-value
mappings.

Proposed error signatures:

```rust
pub enum PolicyError {
    ReservedClassName { name: String },
    OpenKeyClassMalformed { value: String },
}

pub enum RulepackError {
    ReservedClassName { name: String },
    OpenKeyClassMalformed { value: String },
}
```

The v0.5 review should decide whether these variants need `recognizer_id`,
`rulepack_id`, or `surface` fields.

## Open questions for v0.5 brainstorm

- Interner choice: plain `String`, `Box<str>`, `Arc<str>`, or a real symbol
  interner.
- Cross-session counter semantics under open-key classes. Today counters are
  scoped by `PiiClass`; v0.5 must define whether `case_ref` and quoted
  `"case_ref"` are identical after normalization and how that appears in
  snapshots.
- Snapshot v3 to v4 migration shape. v3 entries serialize enum-shaped classes
  and `Custom` names; v4 should serialize normalized keys and preserve existing
  v3 import.
- Whether legacy token aliases are decode-only or also emit under compatibility
  mode. Default v0.5 emission should use one canonical open-key grammar.
- Whether class-priority conflict resolution becomes registry metadata, policy
  metadata, or fixed reserved-name defaults.

## Ship blockers vs nice-to-haves

Ship-blockers: manifest restore round-trip for every emitted open-key token;
fail-closed class-key parsing across policy, rulepack, snapshot, redaction-log
decode, and token restore; exact reserved-name collision variants; preserved
same-class `cooperates_with`; v3 to v4 snapshot migration tests; sanitized CLI
error paths; and docs that preserve drawer `e8b5c041` without growing one CLI
flag per class.

Nice-to-haves: a global interner, compatibility emission mode for
`<Custom:...>`, richer collision diagnostics, custom class-priority policy, and
a new `restore.rs` module if it makes grammar ownership clearer.

#### Crate shape — Option B sketch (decision-deferred)

**Status:** non-binding sketch. Decision moment is v0.5 design review. Acceptance criteria below MUST be met for Option B to land in v0.5; otherwise defer to v0.6 or indefinitely.

**Proposed shape:**
- New crate `gaze-types` carrying recognizer-facing traits + types + adopter-stable serialization shapes.
- `gaze-assembly` collapses; `build_pipeline` moves to `gaze::build_pipeline` behind feature `assembly` (default ON for binary consumers like `gaze-cli`; OFF for plain library consumers).
- `gaze-recognizers` and `xtask` unchanged; external consumer [piinuts/gaze-lens](https://github.com/PIInuts/gaze-lens), formerly the in-tree `debug-proxy`, remains outside the Gaze crate-shape decision.

**Types moving to `gaze-types`** (extraction list — no new public types invented; movements only, per drawer `architecture_853a0593`):

Recognizer-facing traits + structs:
- `Recognizer` (trait) — `crates/gaze/src/registry.rs:15-23`
- `Candidate` — `crates/gaze/src/registry.rs:41-53`
- `DetectContext` — `crates/gaze/src/registry.rs:55-60`
- `Detector` (trait) — `crates/gaze/src/detector.rs`
- `Detection` — `crates/gaze/src/detector.rs`
- `DetectorKind` — `crates/gaze/src/detector.rs`
- `ValidationResult`, `Validator`, `Canonicalizer` (if adopter-customizable)
- `ConflictTier` (referenced by redaction log + DetectContext)

Locale + dictionary supports referenced by recognizer interface:
- `LocaleTag`, `LocaleChain`, `LocaleError`
- `DictionaryBundle`

Adopter-stable serialization shapes (audit-log JSON, manifest format):
- `PiiClass` (must move because open-key refactor lives here)
- `Token` (and any token-shape types)
- `RawDocument`, `CleanDocument`
- `redaction_log::*` public types

**Acceptance criteria for v0.5 to land Option B:**
1. `cargo build -p gaze` (core-only, default features) MUST NOT compile `ort`, `tokenizers`, `ndarray`, or `onig`. Tested via `cargo tree -p gaze --no-default-features` listing.
2. `gaze-types` extraction must move existing public types only; no new wrapper types invented to populate it (drawer `architecture_853a0593`).
3. `gaze-recognizers` continues as the detector trust boundary (axis-4) — no merge into `gaze`.
4. Migration guide section in v0.5 release notes: every `use gaze_assembly::build_pipeline` → `use gaze::build_pipeline` (feature flag). One-line rewrite per call site.
5. Feature `assembly` (or equivalent) MUST be documented with explicit "core-only vs assembly-bundled" guidance for adopters.
6. Bundled with open-key `PiiClass` refactor, NOT shipped as a separate v0.4.x SemVer break.
